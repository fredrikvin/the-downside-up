# Downside Up: detailed usage and configuration

In the VS Code Extensions list and settings, it appears as **Downside Up**.
The Downside Up is a prototype VS Code extension that shows a document-style
Downside Up preview beside your source, like the Markdown preview. It lists the
file's functions at the same position as in the file and adds a plain-language
AI explanation under a function when you ask for one, written for someone who
wants to know what the code does without knowing the language. More local
detail (imports, types, values, and so on) can be turned on in settings.
Explanations are generated only when requested (or prefetched, if you turn
that on), and mock mode is the default and makes no external requests.

For a quick start, see the root `README.md`. Contributor setup and packaging
instructions are in `docs/development.md` (paths are relative to the repository
root).

## Reading code

The **Show callers** icon beside any function opens an incoming-call picker,
independent of the active explanation tab. Select a caller to navigate to its
call site and preview; use VS Code's **Go Back** to return. Only eligible local
files inside the current repository are listed (up to 100 callers).
Native Call Hierarchy is preferred. When unavailable, bundled Go/Rust/Python parsers
scan direct free-function calls, labelled **Statically found callers**. The
fallback reuses package/module dependency resolution and rejects uncertain
receiver methods, interface/trait dispatch, macros, closures, shadowed names,
and ambiguous declarations. It is incomplete: at most 2,000 filesystem entries,
100 loaded files, 2 MiB total text (256 KiB per file), 500 functions, eight
seconds between operations, and 100 results. Native-provider errors are reported,
not silently replaced by fallback results. No results means none found within
the supported analysis and limits, not proof of no callers.
SQL has the same bounded fallback for calls to routines (`CALL`, `EXEC`,
`EXECUTE FUNCTION`, `PERFORM`, and named calls). It matches names, not argument
types, so overloaded routines can show extra candidate callers. It does not
infer dynamic SQL or a live database's schema.
The scan respects exclusions and unsaved buffers, is cancellable, and checks a
selected fallback caller's text again before navigation.
Lookup makes no AI requests. After navigation, current cached explanations
appear normally, and enabled prefetch prioritizes functions near the destination
using existing sharing consent. Opening the picker does not preload its results.

- **Document preview.** By default the preview is concise: the file name, a
  one-sentence AI summary of the file once one of its functions has been
  explained, and a heading per function in source order. **Downside Up ›
  Preview: Include** (`downsideUp.preview.include`) adds imports, types,
  values, locals, standalone comments, modules, and one-line signature descriptions,
  all built locally from the code rather than generated by AI.
  Attached function and method comments are hidden by default; enable **Function
  comments** (`functionComments`) there to show them. This changes display only,
  not the comments available to the AI, and never regenerates explanations. The preview
  follows the active editor and updates as you edit.
- **Scroll sync.** Scrolling the editor scrolls the preview to the matching
  position and vice versa, down to the step or pseudocode line describing
  each code line, and the item at the cursor is highlighted. Clicking in the
  code brings its explanation into view; clicking a step keeps the preview
  still. A function's heading stays pinned at the top while you read its
  explanation.
  Double-click an item to jump to its source.
- **AI explanations.** Click a function's name to navigate to its source.
  Press **Explain** beside it to show its saved explanation, or to generate one if none is
  current. Explanations appear inline, without a repeated accordion label;
  skeleton lines show while they load, with **Cancel** beside the status.
  An explanation gives the function a short
  title (such as "Fetch a wearer"), says what it is for, and lists its inputs,
  its result, the main steps in order, and extras such as cleanup only when
  relevant. When parts of a function run at different times, such as a React
  component's effects and click handlers, the steps are grouped under when
  they run ("Each time it is shown", "When the person clicks Check out"), and
  React components and hooks are explained in React's terms: props as inputs,
  what is shown as the result, and hooks in plain words. The innermost steps at the editor's cursor (or all steps a
  multi-line selection touches) are highlighted, and clicking a step
  highlights its lines in the editor. **Explanations:
  Formats** (`downsideUp.explanations.formats`) adds **Pseudocode** and
  **Flowchart** tabs next to the steps, both enabled by default, with the same highlighting and
  click-to-select; **Explanations: Initial Format** picks the tab that opens
  first. In flowcharts, what a function returns to be shown on screen (such
  as a React element) is drawn as a "Shows" box, and the logic deciding what
  appears inside it, such as a button's label, is drawn inside that box. Choosing a tab switches every explanation, like language tabs in
  documentation, while keeping your place. Enabled views are generated with new explanations; for saved ones,
  open the tab and choose **Generate**. **More detail** adds where it fits, edge cases, language notes,
  and related code; **Explanations: Show Details**
  (`downsideUp.explanations.showDetails`) opens it by default. Current
  explanations stay visible, so the preview reads like a document.
  Several can load at once, and up to six
  generations run at the same time (see **Max Concurrent Requests** below).
  Each explanation links to the related code the extension found.
  Maps and flowcharts fit the preview's reading column: wide rows reflow
  vertically before scaling, with more room for arrows and labels and no
  sideways scrollbar. Very narrow columns may still need smaller text.
  The explanation also uses the functions the function calls, including from
  other files, plus the signatures of the functions those call, and is marked
  outdated when any of them change. For Rust, Go, and Python, it also uses the types,
  constants, and methods the function uses, and their files are described,
  and their functions and calls found, with bundled parsers, so no language
  server is needed. Python supports `def`, `async def`, class methods,
  properties, and nested functions (not lambdas). It follows same-file helpers,
  imports of repository modules, and same-class `self`/`cls` methods without
  Pylance; dynamic dispatch, inheritance, star imports, and re-exports are not
  resolved. SQL uses a bundled lexer to find `CREATE FUNCTION`, `PROCEDURE`,
  `TRIGGER`, and `VIEW` (including materialized views), plus tables, types,
  indexes, sequences, and standalone queries. Schema objects and queries stay
  visible with the default concise settings. Table cards show columns, types,
  required/optional values, defaults, generated expressions, keys and foreign-key
  relationships. Column and same-file relationship links navigate to
  host-validated source locations. Same-file `ALTER TABLE` keys/defaults and
  `CREATE INDEX` statements are folded into their owning table. Enum values and
  sequence definitions are shown locally. **Explain** is available for schema
  objects as well as queries; data objects do not show a caller button.
  sqlc `-- name: QueryName :mode` annotations name queries and describe whether
  they return one/many rows or execution results; unnamed statements get
  numbered headings. Query previews list inputs and syntactically referenced
  relations. Common PostgreSQL dollar bodies, MySQL `DELIMITER`,
  T-SQL `GO`, and SQLite trigger blocks need no database or language server.
  Related table/view definitions and routine calls are resolved from eligible
  `.sql` files, with basic schema qualification and `SET search_path`/`USE`
  context. Ambiguous schema names are omitted; overloads are candidates matched
  by name. Duplicate definitions use the last lexical file/statement, with a
  limitation, not actual migration execution order. Lookups inspect at most
  100 files, 2 MiB (256 KiB per file), and 160 references within the shared
  deadline and dependency budgets. Table constraints/indexes are included in
  explanation context and freshness tracking. ALTER association is same-file
  only, not migration replay; not every ALTER operation is interpreted.
  Dynamic SQL, non-SQL routine bodies, and embedded SQL are not resolved.
  This is not a complete dialect parser or database catalog.
  SQL contributes no import-diagram edges.
  JavaScript and TypeScript (including JSX and React) are
  described and their functions found with bundled parsers too: arrow
  functions, components (also inside `memo` or `forwardRef`), hooks, and
  class and object methods are all functions you can explain, and the
  preview labels components and hooks and describes state in plain words.
  What such a function uses (the functions and hooks it calls, the components
  it renders, and the types it names, such as its props) is found with VS
  Code's built-in TypeScript go-to-definition; right after VS Code starts,
  this waits for TypeScript to load the project. Other languages use the
  editor's own tooling: functions come from its document symbols and calls
  are found with go-to-definition, so this works where a language extension
  provides them.
  Current saved explanations appear whenever the preview shows their file,
  including after reopening the preview or restarting VS Code; this is a
  local cache check only. The file summary is generated with the first new
  explanation in a file and sends that file's text (up to 24 KiB).
  Selecting text inside a function
  in the editor opens its section only when a saved explanation exists.
  Selecting never starts generation by itself.

**Downside Up: Open Preview to the Side** (the preview button in the editor
title bar) opens or reveals the preview of the active file, following the
editor's position. If text is selected inside a function, it also opens that
function's explanation, generating or regenerating it when none is current, so
selecting a function's name and opening the preview explains it. With a plain
cursor it only opens the preview. The repository context used for explanations is shown at the
end of the preview.

**Changes.** With the preview open, showing a native VS Code diff of local Git
changes switches it to a change view of that pair; **Explain changes** sends
both versions of that file to the Functions model (asking for sharing approval
like any explanation) and saves the result in the repository cache. Opening
a diff, or **Open Preview to the Side** from either side of one, looks up a
saved explanation first. With **Prefetch: Enabled** and sharing already approved
for the repository and Functions model, a missing comparison preloads in the
background, including paired Steps, Pseudocode, and Flowchart views. It never
prompts for consent or regenerates an outdated comparison after an edit.
Invalid cross-side matching no longer hides otherwise valid charts: the
matching is omitted with a specific limitation. Invalid source references
still reject their visual scope, without discarding other valid scopes.
**Review Changes…** confirms a count of file comparisons,
explains them in the background like prefetching, and opens each in its native
diff. Binary, oversized, excluded, and identical files are skipped. See
`docs/prototype.md` for the scope and limits.

**Preview header.** A shared sparkle icon groups two compact model buttons,
each opening its picker directly: **Project overview** first for project priming,
repository context reviews, architecture maps, folder summaries, and main flows;
then **Functions** for function explanations, added formats, and file summaries.
Each shows its role beside the current model, even when both use the same model.
They wrap in narrow sidebars without hiding either role. Tooltips explain what
each model does. Header buttons are transparent and borderless until hover or
keyboard focus; Clear turns red on interaction. **Clear** is a repository-wide
icon button with a label that collapses in narrow sidebars. Clear keeps its confirmation
and removes saved sharing consent as well as this repository's cached results.
Clear and page actions are disabled while requests are active; Cancel remains available.

**Initialize project** is a separate repository-wide
button above the divider, visible when no saved repository overview exists,
including immediately after Clear. It explicitly builds the overview and map
using the normal sharing approval. Clearing alone never starts generation.
The architecture map sits beneath the opening description, without a redundant
Map heading or arrow-description paragraph; hover for provenance and limitations.
The page heading below the divider has a **Refresh** icon for checked outdated
items on that page. It is disabled when none are known to need updating.
The project page also has a labelled **Map project** action when missing, or
**Update project map** for a map made with different model/settings. These
map actions are separate requests; they do not expand the outdated-item batch.
Amber on the divider means known outdated content, not a repository-wide
freshness check; animated blue takes precedence while working. Success does
not leave a persistent message. Errors remain visible.

The header shows **Tokens in current cache**. Expand it for recorded input/output
tokens, totals for **Overview** and **Functions**, and a per-provider/model breakdown.
Overview includes mapping, folder summaries, and main flows; Functions includes
explanations, added formats, and file summaries. Only retained records contribute:
replacing a record replaces its usage, and Clear resets the total. This is not
lifetime usage or billing, and failed/cancelled requests are not included.
Estimated totals use `~`. The disclosure also counts saved explanations, file
summaries, folder summaries, and flow sets across **all models**, plus map age.
These are local cache reads, not a repository-wide freshness scan;
map age does not mean it is current. **N outdated here** counts
only saved items checked here: shown function explanations and the file summary,
or the folder's displayed summary, flows, and directly listed file summaries.
It does not include nested folders. The page **Refresh** icon explicitly
requests fresh versions of that fixed set, asking for sharing approval as
needed. Zero outdated counts are hidden. Cancel stops remaining requests; completed results stay saved.
Version 0.31.0 updates the local cache schema; use Clear for older caches when prompted.

**Folder and project previews.** A folder can be previewed like a file: run
**Open Preview to the Side** on a folder in the Explorer, run **Downside Up:
Preview Project** for the repository root, or click a step of the breadcrumb
trail (`project › folder › file`) at the top of any preview. A folder preview
lists its subfolders (with how many files they hold) and files, with each
file's saved one-sentence AI summary, and draws a **structure diagram** of
which of them import which: importers above what they import, so entry points
sit on top and foundations below; folders that most of the others use sit in
a bottom row without arrows, and items with no imports to or from the others
in a row of their own. Click a box or name to preview that folder or open
that file. The diagram is built locally from imports (Rust, Go, Python, JavaScript,
and TypeScript, including `tsconfig` path aliases); Python follows absolute
and package-relative imports under the repository root or a `src/` layout.
It does not show other
connections, such as dependency injection or calls between services, and
nothing is generated or sent. The folder preview stays until you switch to
another file.
Breadcrumb icons identify the project, groups, components, modules, support
folders, plain folders, and files using the saved project map. Project, group,
and component crumbs are tinted chips to highlight their richer pages; hover
for the level and saved description. Without a map, only the root is marked
as a project and other directories use plain folder icons. Loading the icons
is cache-only; opening the project page still requests a map when none is current.

**The project map: one zoom level at a time.** When the repository is primed
(with the first explanation, when the project preview opens without a current
map, or with **Refresh Repository Context**), the overview model also maps
the project: its parts, the level of each folder, and how the parts connect.
Opening the project preview is the request: the first time in a repository
it asks for code-sharing approval like an explanation, and the page shows a
placeholder while the map is made. If you decline, cancel, or it fails, it is
not tried again on its own until VS Code restarts; choose **Map project**
instead. Each folder preview then shows what fits its level:

| Level | Example | The preview shows |
|---|---|---|
| Project | the repository root | two or three sentences, a **map** of the components and outside services with labelled connections (such as GraphQL, REST, or MQTT), the main parts, and flows between parts |
| Group | `services/` | its members with one sentence each, and a map of how they connect to each other and to the rest |
| Component | `services/inventory` | what it is, what it offers and uses, a map of its internal parts and outside connections, and flows between them |
| Module | a folder inside a component | its files, import structure, and flows through files and functions |
| Support | `docs/`, `tools/` | a short description and its contents; no charts |

Folders the map does not list take their level from the closest mapped folder
above (inside a component they are shown like modules), and anything else is
shown as a plain folder with its files and import structure. A project whose
map has no separate components, such as a single library, is shown that way
too. Boxes on a map open their folder; outside services (such as devices or
a message broker) are drawn with dashed, rounded borders. The map is saved
with the repository overview and reviewed with it when the repository changes
(a new or removed file, a changed manifest or README, or a branch switch, at
the next new explanation or refresh), never on its own; it is saved apart from
the overview, so a changed map never outdates explanations.

To map the project, priming lists the repository's files breadth-first (up
to 2,000, so every area is covered at its top levels), ranks them by name and
location, and reads only what it may send: READMEs, manifests
(`package.json`, `go.mod`, and others), API contracts (OpenAPI, AsyncAPI,
GraphQL schemas, protobuf), Dockerfiles, and deployment files, then entry
points and a few other files; test folders and generated code are not read.
Each kind gets a share of a bounded budget (64 KiB of files, most cut at
6 KiB), so no kind crowds out the others in a large repository. Priming also
sends a bounded outline of the repository's folders with these markers.
Explanations read the related files they need on their own, so what priming
read does not limit them.
Compose, Kubernetes, and Helm files are sent only as names: resource kinds
and names, services, images, ports, environment variable names, and config
keys, never their values. **Project Map: Detail**
(`downsideUp.projectMap.detail`) chooses `brief` (one sentence per part) or
`detailed` (also a few sentences per component with what it offers and uses,
so component pages need no extra request, at the cost of a larger priming
request). Changing it maps the project again with the next new explanation or
refresh.

A folder can also get an AI summary: choose **Summarize this folder** at the
top of its preview (the project and groups are described by the map
instead). It gives one sentence on
what the folder is for, a few on how its parts fit together and where to start
reading, and a sentence for each file or subfolder that has no summary of its
own (marked as inferred from names). For a component, it also says what the
component offers and what it uses. The request holds only names: the
contents' names and saved summaries, the names of functions and types in
files without a summary, the imports between them, and the folder's README;
no code, except that a component's request includes its API contracts (up to
16 KiB, from files that may be shared). Support folders get a shorter
summary. Summarize subfolders first, and their summaries feed the parent's;
a subfolder without a summary of its own uses the map's sentence about it.
A saved summary is shown whenever you preview the folder, and marked
outdated when its contents change; choose **Regenerate** to update it.

**Describe the main flows** draws one to three flowcharts of what happens,
such as a person using the app, data arriving from devices, or startup, at
the level of the preview. In the project, group, and component previews, the
steps pass between the parts on the map, and clicking a step opens that
part's folder; the request holds the map's parts, their one-line summaries,
and how they connect. In module and plain folder previews, each step names
the file and function where it happens, and clicking it opens that place; the
request holds file paths, saved file summaries, function names, and the
imports between parts, so explaining a few functions first (which saves file
summaries) gives better flows. Neither request holds code, and the extension
only links to parts, files, and functions it found itself. Support folders,
and the project before it is mapped, have no flows.

**Summarize with all subfolders** does both for a whole tree in one go. It
first checks every folder below locally, then says how many requests it will
send and roughly how many tokens, and sends nothing until you accept. It then
summarizes each folder without a current summary, deepest first so every
summary builds on its subfolders' new ones, and finally describes the main
flows if they are not current. Up to 100 folders are summarized per run (in
trees of at most 400 folders); for larger trees, start with their subfolders.
The preview shows the progress, and **Cancel** (or changing the overview
model) stops the run; finished summaries are kept.

Project-level work (the repository overview and project map, folder
summaries, and flows) happens far less often than explaining functions, so it
can use a stronger model:
run **Downside Up: Choose Overview Model**, which sets
`downsideUp.languageModel.overviewModel` (or, with OpenAI, set
`downsideUp.openai.overviewModel`). Explanations keep using the regular model.
Code sharing is approved once per repository and model, so a new overview
model asks once.

## Provider setup

While requests are active, the header divider animates and the preview shows the current
stage, and elapsed time. Slower models may take several minutes; VS Code
language-model requests allow up to ten minutes, and you can cancel at any time.
Elapsed time is not an estimate of completion time.

The `downsideUp.provider` setting defaults to `mock`. Mock output is
deterministic placeholder content, not semantic analysis. There are two live
providers, each with its own section in the extension's settings (**VS Code
Language Models** and **OpenAI**) holding its explanation model and its
optional overview model.

### GitHub Copilot or another VS Code language model (no API key)

1. Sign in to GitHub Copilot in VS Code (or install another extension that
   provides language models).
2. Run **Downside Up: Choose Language Model** and pick a model. This sets
   `downsideUp.provider` to `vscode-lm` and saves the model's name, for
   example `Claude Opus 4.5`, in `downsideUp.languageModel.model`. In the
   settings, the **Choose…** link under the setting opens the same picker.
3. Explain a function. Before the first request for a repository and model,
   review and accept the code-sharing prompt. VS Code also asks once whether
   Downside Up may use language models; you can change that later under
   **Accounts › Manage Language Model Access**.

Requests go through the VS Code Language Model API and use your existing
subscription, so they count toward that plan's usage limits and follow that
provider's data-handling terms and your organization's policies.

### OpenAI API key

1. Set `downsideUp.provider` to `openai`, and pick the model in
   `downsideUp.openai.model`.
2. Run **Downside Up: Set OpenAI API Key**. The key is stored in VS Code
   SecretStorage.
3. Explain a function. Before the first external request for a repository and
   model, review and accept the explicit code-sharing prompt.

OpenAI API access and billing are separate from any coding-assistant
subscription. The extension sends bounded repository context and selected
source to the OpenAI Responses API; `store:false` does not guarantee zero
provider-side retention. See `docs/prototype.md` for data handling, cache
freshness, limits, and known limitations.

### Content exclusion and enterprise policies

The extension never explains, prefetches, or sends as context any file that
is excluded by `.gitignore` or `.copilotignore` (at any folder level inside
the repository, and `.copilotignore` in folders above it), by VS
Code's `files.exclude` or `search.exclude`, by being in a hidden, dependency,
build, or vendored folder, or by having a secret-like or generated name.
Explaining a function in such a file stops with the reason before anything is
sent, and the preview notes it; local descriptions are still shown.

GitHub Copilot's content exclusion, which organization and repository
administrators configure on GitHub, is **not** applied to this extension's
requests, even when the model is a Copilot model. GitHub enforces those rules
in Copilot's own features; this extension builds its prompts itself and sends
them through VS Code's Language Model API, so Copilot cannot tell which files
the text came from. To apply your organization's rules, mirror the excluded
paths into `.copilotignore` files in each repository, using the same path
patterns. With an OpenAI API key, no Copilot policy applies at all; check that
your organization allows sending source code to OpenAI before using it.

If your organization enforces content exclusion with its own policy files on
each computer (some organizations keep these for Copilot hook scripts), point
these settings at them. Use **Choose file…** beside each setting, or **Choose policy
folder…** to select a folder once and assign its files to the three policies.
Filenames are not guessed; **Keep current setting** skips a policy, and cancelling
before saving changes nothing. Selecting a file stays on that step: use the
**Next** button to continue, or **Back** to revise a previous choice.
The setup panel uses radio-button file choices, without a textbox. Each step shows
progress and examples of the expected contents.
A final review lists all three assignments; use **Save** to apply them.
Only regular files directly in
that folder are listed, without reading their contents or scanning subfolders.
These actions are also available in the Command Palette under **Downside Up**.
Each picker saves local absolute paths to user settings only. You can still type
a path manually. Policy files are plain text with one entry per line;
blank lines and lines starting with `#` are skipped, and `~`
is expanded. They are read from user settings only, so a repository cannot
change them, and take effect immediately. An empty setting, or a file that is
missing or unreadable, adds nothing, so check the paths.

Use **Downside Up: Check Content Exclusions…** in the Command Palette (or the
link beside any policy setting) to inspect their load status, resolved user paths,
active rules, and original line numbers, including ignored comments and blanks.
Missing or unreadable files show **This policy is not active**, not an all-clear.
Choose **Test current file** or **Test a file…** to see the actual exclusion decision,
matched rule and origin, and any restricted-remote rule or repository opt-in.
The report is an unsaved plain-text document; rerun the command to refresh it.
Checks bypass cached policy/parent-ignore decisions and run locally, without AI
requests, consent changes, or recursive scans. File checks
require a trusted local workspace. They read only policy/ignore/opt-in control
files and Git metadata, not source contents (unless the tested file itself is one
of those control files). The first blocking check is shown; other rules may also
match. **Not excluded** does not mean safe to share: consent,
supported file types, and request/scan limits still apply. GitHub Copilot's
server-side exclusions are not available to this extension or applied to Language
Model API requests.

**Exclusion: Blocked File Patterns File**
(`downsideUp.exclusion.blockedFilePatternsFile`) lists gitignore-style
patterns for files that are never read into context or sent, in any
repository. Patterns are matched against paths inside the repository: one
without `/` matches at any depth, one with `/` is anchored at the repository
root, and a pattern matching a folder covers everything in it. `*` and `?`
stay within one folder; `**` crosses folders.

```text
# Deployment settings with credentials
deploy*.yml
*.vault
# A whole folder, wherever it is
private-assets
# Only at the repository root
docs/internal
```

**Exclusion: Restricted Remotes File**
(`downsideUp.exclusion.restrictedRemotesFile`) lists Git remote URL prefixes.
`*` matches any characters, and a trailing `*` is implied. A repository with
any matching remote is not read or sent at all (explanations, file summaries,
and **Refresh Repository Context** stop with the reason, while the local
preview keeps working) until it opts in with one of:

- a `.copilotignore` file at its root or in a folder above it (an empty file
  allows everything; patterns in it exclude files as usual),
- a `.allowed-services` file at its Git root that contains the word
  `copilot`,
- a listing in the allowed repositories file below.

```text
# Every repository on these servers
ssh://git.example.com/
https://git.example.com/
https://*.internal.example.com/
```

**Exclusion: Allowed Repositories File**
(`downsideUp.exclusion.allowedRepositoriesFile`) lists repository paths that
may be sent even when their remote is restricted. A remote's path is its URL
without the scheme, user, host and port, and `.git`: for
`ssh://user@git.example.com:29418/team/app.git` it is `team/app`. `*` matches
within one path segment, and the whole path must match.

```text
team/app
# Every repository directly under tools
tools/*
```

### Request size

**Max Request Size** (`downsideUp.maxRequestSize`, default 96 KiB, 32 to
512) caps each explanation, added view, file or folder summary, and main
flows request. A request that would be larger is not sent, and the error
says how large it would be. Raise it for very large functions with much
related code; lower it to cap what each request costs. The model's own input
limit still applies. **Max Project Context Request Size**
(`downsideUp.maxProjectContextRequestSize`, default 256 KiB, 128 to 1024,
user settings only) separately caps repository overview and project map requests.
Increasing it does not expand the scanner's bounds, start generation, or
invalidate saved results; the next requested generation uses the new limit.
That limit includes the previous overview and map when reviewing repository
context, not just the file being explained. If a review would be too large,
the same action rebuilds context from current bounded evidence in one request.
Inventory is shortened further if needed to fit the complete serialized prompt;
the overview's limitations disclose rebuilding and truncation.

### Prefetching (optional)

By default, explanations are generated only when you ask for one. To have them
ready as you read, turn on **Downside Up › Prefetch: Enabled**
(`downsideUp.prefetch.enabled`) in your user settings, or choose **Enable prefetch**
in the one-time prompt when you first open the preview. **Not now** or dismissing
the prompt leaves it off; an existing user-level choice is respected.
The prompt discloses quota/billing and the separate sharing approval.
While the preview is
open, the extension then explains the shown file's functions in the
background, starting where you are and spreading outward. It uses the
request slots your own requests leave free and always leaves one for them;
**Max Concurrent Requests** (`downsideUp.maxConcurrentRequests`, default 6,
1–8) sets how many requests run at once. More is faster but may hit your
provider's rate limits sooner; it does not change how many requests are made. **Prefetch: Window**
(`downsideUp.prefetch.window`, default 10) limits it to that many functions
nearest your position and follows you through the file; `0` prefetches every
function. **Prefetch: Dependencies**
(`downsideUp.prefetch.dependencies`, default 3, `0` for none) also prefetches
up to that many functions in other files that the function you are reading
calls, right after the function itself, so they are ready if you follow a
call. Prefetching runs only in trusted workspaces with code sharing approved
for the repository and model (and the overview model, if separate). Until
then, a persistent banner offers **Approve sharing**. Clicking it explicitly
opens the sharing dialog for each model still needing approval; accepting
starts prefetching. You can also approve by explaining a function first.
Declining keeps the banner available without retrying the prompt.
Background work never asks for approval on its own. Loading explanations
show skeleton lines inline as they are queued or generated. Every prefetched explanation
counts toward your provider's usage limits or billing.

This setting also preloads the Git diff first shown in the preview, using
only the Functions model and its existing sharing approval. Saved comparisons
are reused. File edits, cursor movement, and refreshes never generate a new
comparison; use **Explain changes** to update an outdated or failed one.
Diff prefetch uses background request priority, stops on cancellation or when
disabled, and does not automatically retry failures. Review Changes batches
keep their own confirmed scope and do not also prefetch the shown diff.
Comparisons use the current Functions model, with compact visuals focused on
the changed behavior rather than full-file diagrams; no separate review model
or additional model calls are needed. The model defines each visual operation
and source span once; the extension constructs the linked views locally while
preserving explicit text order and graph connections.

If a response fails, the error distinguishes `incomplete-json` (appears cut
short), `malformed-json`, and `invalid-schema`, and shows the received character
count. These diagnostics contain no response excerpts or source text and do
not cause another model call. Incompleteness is a diagnostic hint, not proof
of a model output limit; retry success alone does not establish the cause.

Recent function context is reused within the session while the selected document
and its tracked files and unsaved buffers are unchanged. Clicking or refocusing the
editor does not invalidate explanations just because language tools answer
differently under load; actual source edits still trigger freshness checks.

**Formatting changes:** Go, Rust, Python, JavaScript, and TypeScript use syntax-aware
fingerprints for functions, imports, dependency signatures, caller files, and
file summaries. Indentation, spacing, and blank lines do not outdate them;
literal contents, comments, and syntax-sensitive newlines remain meaningful.
In Python, changing indentation that changes the parsed structure outdates
the explanation; reindenting without changing structure does not.
SQL uses lexical fingerprints: ordinary comments, whitespace, and unquoted
casing are ignored; quoted identifiers, string contents, and operator
boundaries are preserved. SQL/PL/pgSQL dollar-quoted routine bodies are
normalized as SQL, while other dollar literals and non-SQL bodies remain
literal. Executable comments and optimizer hints remain meaningful. A change
to a referenced table or view definition also outdates an explanation.
sqlc name/result-mode annotations are meaningful inputs and remain tracked.
Other languages conservatively ignore line-ending differences, trailing spaces,
and blank lines while preserving indentation and in-line spacing; potential
multiline literals or continuations fall back to exact text.
Caller evidence is tracked per file, not by line number; a meaningful change
elsewhere in that caller file can also outdate an explanation. Formatting and
unrelated file edits do not discard an explanation already being generated.
Line links follow spacing and blank-line shifts when their anchors still match;
reflowed or unresolvable links are left unlinked rather than guessed.

### Review mode

To review a branch or a pull request, check it out and run **Downside Up:
Review Changes…**. Choose what to compare the checked-out code with: the
branch's merge base with `main` (or `master`, or the remote's default
branch), that branch as it is now, only uncommitted changes, or any recent
commit. The extension finds the functions that changed locally (including
uncommitted edits and new files), tells you how many, and after you confirm,
explains them in the background with the request slots your own requests
leave free, so their explanations are ready when you get to them. In the file
you are reading, the changed function nearest your cursor goes first, so
jumping to a changed function that is still waiting moves it forward;
everything else uses the preview as usual. Functions that already have a
current explanation are skipped, as are files excluded from AI explanations.
The status bar shows progress; click it (or run **Downside Up: Show Changed
Functions**) to jump to a changed function, or to stop. Closing the preview
or **Cancel** stops it too. Running the command is an explicit request, so it
asks for code-sharing approval if needed, and every explanation counts toward
your provider's usage limits or billing.

### Saved explanations on hover

Hovering a call to a function shows the purpose from its saved AI
explanation, if one is current. Calls are found the same way as for
explanations, so outside Rust, Go, and Python this needs
go-to-definition (built in for JavaScript and TypeScript, where hovering a
rendered component such as `<CartItem>` works too). This only reads the local cache and never
generates; turn it off with **Downside Up › Hover: Saved Explanations**
(`downsideUp.hover.savedExplanations`). It works once the extension is active,
for example after opening the preview.
